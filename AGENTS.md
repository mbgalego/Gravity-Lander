## Collision Hulls (`collisionPolygon`) — Units Trap (THE reason Nutcracker rocks passed through)
- `vulcan` (~line 1044), `nutcracker` (~line 926) and `eagle` (~line 998) define a custom `collisionPolygon` in `src/game/ships.ts`; other crafts fall back to a localPoints-derived hull in physics.ts. It is an OPTIONAL per-config `collisionPolygon: [{x,y}, …]`.
- Eagle hitbox (37 vertices, raw coords × 1.58): covers quad fusion engine block + tanks (aft x to −112.2), dorsal truss + hazard collars + raised bridge (top y to −29.2), RCS outrigger pods, cargo pod, the W-shaped belly pocket tracing the two VTOL bell flares + pylons, both landing-gear footpads (bottom y 38.9, x ±64), and the beak cockpit + nose probe tip (fwd x to +107.9, scaled from raw 68.3). Verified by executing `drawEagle` against a recording mock ctx: all 15,486 sampled solid points inside with ≥0.3 scaled-unit margin.
- How physics uses it (`src/game/physics.ts` ≈line 1839): `polyWorldPoints = config.collisionPolygon.map(lp => transformPoint(lp, ship.pos, ship.angle))` → STRICT rigid-body transform (rotation + translation), NO scale. Collision = edge-to-edge per hull edge (terrain/obstacle) + point-in-polygon from vertices AND edge midpoints (weight 1.0; landing-gear feet 0.6). Ground/terrain contact is driven by these polygon points, so an undersized polygon both lets rocks through AND makes the ship float/sink wrong vs the sprite.
- THE TRAP: draw fns (`drawNutcracker`, `drawViper`, … in `shipDrawers.ts`) run under `ctx.scale(renderScale)`, so every coordinate inside them is RAW SVG units (viewBox ≈ -40..40). A `collisionPolygon` written in raw units is ~renderScale× too small (Nutcracker = 1.70×) — exactly the bug fixed in 12b488b. Polygon coords MUST be raw × renderScale, same convention as `localPoints` (e.g. leftFoot.y 57.8 = footPadY 34 × 1.70).
- How to derive one correctly (proven on Nutcracker): (1) extract every SOLID shape's coords from the draw fn; (2) for rotated sub-assemblies apply the SAME transform chain first (e.g. drill arm `translate(-40,-21); rotate(-0.24 rad)` — get the true extremum, not the unrotated bbox); (3) EXCLUDE translucent light/beam FX — the searchlight cone is a non-solid visual, its hull beneath is what needs covering; (4) × renderScale; (5) trace a single clockwise hull (no holes) enclosing ALL derived points; (6) VERIFY with a throwaway python script (ray-cast every sampled draw point inside the polygon, no self-intersections, origin (0,0) inside) + `npx tsc --noEmit`. In-game the debug `renderShipHull` overlay draws the polygon over the sprite — eyeball that before playtesting.
- Menu SVG (`ShipGraphic.tsx`) is separate art and does NOT define the hitbox; only the canvas draw fn's geometry matters.

## Craft Import / Update Playbook (external-AI SVG → game, proven 2×)
Step order that NEVER fails, plus the hard-won gotchas:
1. **Save SVG → validate first** (no game edits until it passes): check viewBox -40 -40 80 80, all coords within ±40, no filter/mask/clipPath/text/image/style, required `data-part` inventory (hull, wing, canopy, landing-gear, ≥2 footpad, detail, engine×L/R), mirror symmetry, and STATS ranges (mass .7–3.0, thrust .7–1.6, torque .85–1.5, renderScale 1.25–1.6). Render + pixel-sample BEFORE importing.
2. **Canvas splice — CRITICAL, do not guess the successor**: in `shipDrawers.ts`, `drawViper` is followed by `drawAegis` and `drawWasp` by `drawKestrel` — NOT alphabetical neighbors. Use python `src.index('export function draw<Target>(')` → `src.index('export function draw<ActualNext>(')` with ActualNext confirmed by `grep -n '^export function draw'`. After writing, sanity-check `len(src)` grew by +2–5k; a drop of ~100k means you ate Vanguard/Goliath/Behemoth/Leviathan/Mammoth (restore with `git checkout -- src/game/shipDrawers.ts` and redo).
3. **Gradients**: SVG defs are `objectBoundingBox` (a single def auto-fits every element, including horizontal pod shaders). Canvas is user-space: create ONE `createLinearGradient` PER element bbox (e.g., separate L/R pod and L/R cylinder gradients). Always `.addColorStop` in the same order as the SVG stops (incl. 0.x offsets).
4. **Opacity**: source per-element `opacity="0.8"` double-composites where shapes overlap; a JSX `<g opacity>` or a single shared `globalAlpha` unions them → subtly different pixels. Keep PER-SHAPE opacity in both JSX (attr on each element) and canvas (`ctx.globalAlpha` set per fill). resvg pixel diff ~40–60 caught this — see verification step 9.
5. **ViewBox overflow**: canvas never clips but the menu SVG does. Nudge any element past ±40 (e.g., antenna tips moved y=-40→-39.4, r .8→.7) in BOTH sources so the card doesn't crop.
6. **localPoints anchors** = SVG local × renderScale: nose (0,−38)×r; footpad centers → `leftFoot/rightFoot` (use pad.y×r, keep x from pad center); engine anchor = nozzle EXIT-PLANE center (the edge with max y, average its x endpoints) — NOT the polygon centroid; `data-engine="center"` has NO game support (dual-thruster only) → static detail, no flame/anchor. Also refit shoulder/hip localPoints to the new silhouette (they feed collision flanks + scorch FX).
7. **Spring gear in draw fn**: pads must stay planted while the renderer translates the hull → `const footPadY = padLocalY + gearSpringOffset;` draw pads at that y (isolated beginPath each) and stop struts at `footPadY − padHalfH`.
8. **Paint order** in the draw fn must replicate the SVG document order exactly (details layer last — e.g., the Viper keeps panel seams OVER the nose stripe per source; the Wasp decals are last so they sit on top of the hull).
9. **Pixel-parity verification** (fast & reliable; do it every time): regex-extract the new `{modelId === 'x' && ( <g>…</g>` block + that craft's gradient defs from `ShipGraphic.tsx` → camelCase-attr→kebab (`strokeWidth`→`stroke-width`, `stopColor`→`stop-color`, `strokeOpacity`→`stroke-opacity`) → wrap in `<svg viewBox="-40 -40 80 80">` → render with `@resvg/resvg-js` (temp-installed in `/tmp/viper-check`) → sample 15–25 coords (hull, wings, canopy, nozzles, accents, decals, footpads) and require identical RGB (≤30 sum tolerance) vs the user-approved source SVG. 22/23 or 14/14 parity = menu card synced.
10. **Finish**: `npx tsc --noEmit` → 0; dev server is `vite` (HMR, no restart needed; pid via `ss -ltnp | grep 3000`, binds 0.0.0.0:3000); confirm new code served by curling the transformed module from `http://127.0.0.1:3000/src/...`; update the `CRAFT_SVG_SPEC.md` contract only if rules changed; record the config/stats `ships.ts` re-tune (anchors, footpadSpan=padX×2×r, stat bars, colors, lore) in the per-craft AGENTS.md bullet.

## Landing Gear & Canvas Path Isolation (NEVER CONNECT FOOTPADS)
- In HTML Canvas (`shipDrawers.ts`), methods like `arc`, `ellipse`, and native `roundRect` will automatically draw an implicit connecting line (`lineTo`) from the previous subpath endpoint if called consecutively within the same subpath before `stroke()`.
- Disconnected symmetrical components (especially left and right landing gear footpads, knuckles, sensors, or twin thruster bells) MUST NEVER share an open subpath.
- ALWAYS isolate them: either call `ctx.beginPath()` / `ctx.fill()` / `ctx.stroke()` per footpad, or explicitly `ctx.moveTo()` to the start of the next shape.
- The `roundRect` helper in `shipDrawers.ts` is implemented with an explicit `moveTo(x + radius, y)` and `arcTo` to avoid browser-native connecting lines between consecutive rects.
## Custom Map Storage (src/utils/customMapsStorage.ts)
- `STORAGE_KEY = 'gravity_lander_custom_maps_v4'` (localStorage). Fresh installs seed it with `STARTER_TEMPLATES`; `syncOfficialMap` then merges every `OFFICIAL_*_MAP` (inserts if missing, replaces when `officialMap.updatedAt > saved.updatedAt`) — in-memory only, NOT persisted, but re-synced on every `getSavedCustomMaps()` call.
- To make/update an official planet map, FOUR places must stay in sync (Hyperion is the model): (1) the `OFFICIAL_<NAME>_MAP` constant, (2) add it to `STARTER_TEMPLATES`, (3) add a `cleanId === '<planet>'` branch in `getSavedMapForPlanet` (BOTH the main fallback AND the catch fallback), (4) add `<planet>` to `isOfficialMap`'s list + a branch in `getOfficialDefaultMap`. Missing any of these = fresh players never see the map (it falls back to procedural terrain).
- Launching an official planet that has a saved override goes through `handlePlayCustomMap` → `saveLastPlayedPlanetId('custom-official-<planet>')` (same as Hyperion). A stale `updatedAt` in an old constant is what lets new map versions auto-propagate to existing players.
- Map editor exports are plain JSON with the same schema as `CustomMapData` (identical top-level keys). Converting JSON → TS constant: emit with single-quoted strings, compact one-line array elements for flat nodes, multi-line for `customTheme`/launch pads/polygon obstacles, trailing commas — then verify by transpiling with esbuild and deep-comparing in Node (regex JSON re-parse is NOT reliable).
- `promethean_core (1).json` in repo root is the user's export that seeded the current `OFFICIAL_PROMETHEAN_MAP` (gravity 4.9, targetTime 500s, 27 obstacles, 10 fuel pickups, 5 cargo platforms).
